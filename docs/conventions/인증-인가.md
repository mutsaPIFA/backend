# 인증·인가 컨벤션

> **인증 방식 자체(access+refresh 쿠키·회전)의 결정 근거는 팀 계약이 단일 소스다** — `docs/api-v1.md` "인증 구조" + 결정로그. 여기는 그 위에서 **백엔드 코드를 쓸 때 지키는 규칙**만 다룬다. catalog/closet/styling 전부 해당.

## 사용자 정보 주입 — 컨트롤러 레벨

```java
@GetMapping("/api/v1/closet-items")
public List<ClosetItemResponse> list(@AuthenticationPrincipal Long userId) { ... }
```

- 인증된 사용자 id는 **컨트롤러에서 `@AuthenticationPrincipal Long userId`로 주입**받는다. `JwtAuthFilter`가 심어둔다.
- **서비스·도메인 계층에서 `SecurityContextHolder` 직접 조회 금지.** 사용자 컨텍스트는 컨트롤러 → 서비스로 **파라미터로 전달**한다.
  - 이유: 서비스가 시큐리티 인프라에 묶이지 않아야 테스트가 단순해지고("userId 5라고 치자"로 끝), 어떤 유저 컨텍스트로 도는 코드인지 시그니처만 봐도 보인다. (tech-blog ADR-0001과 같은 결정)

## 엔드포인트 보호 — 기본값은 잠금

- **새 엔드포인트는 기본이 인증 필요다.** 아무것도 안 하면 잠긴다 — 이게 의도.
- 공개 경로는 `SecurityConfig.PUBLIC_PATHS` **한 곳**에만 추가하고, 계약(`api-v1.md`)의 "공개 엔드포인트" 목록과 항상 일치시킨다. 계약에 없는 경로를 임의로 열지 않는다.

## 인가 — 역할 없음, 소유권 검사

- v1에 역할(Role)·권한 체계는 **없다.** 인가 = "본인 리소스인가" 하나뿐.
- 소유권 검사는 **서비스 계층**에서: 리소스의 `userId` ≠ 요청 `userId` → **403 "권한이 없습니다"**, 리소스 자체가 없으면 **404**. (계약 에러표의 403/404 구분 그대로)
- 검사 없이 `findById`만 하고 반환하는 조회를 만들지 않는다 — 남의 옷장이 보인다.

## 에러 — 401은 전역에서만

- 인증 실패(토큰 없음/만료) 401은 **entry point와 전역 예외 핸들러가** 계약 형식으로 만든다.
- 개별 컨트롤러·서비스에서 인증 관련 에러 응답을 직접 만들지 않는다.

## 토큰

- 토큰 생성·검증 로직은 **`shared/config/JwtTokenProvider` 한 곳**. BC에서 JWT 라이브러리 직접 호출 금지.
- refresh 토큰 저장·회전·로그아웃 무효화 규칙 → [`DB-컨벤션.md`](DB-컨벤션.md) "Refresh Token".
- 프론트 관점 계약(쿠키 속성, `withCredentials`)은 `docs/api-v1.md` — 백엔드가 임의로 바꾸지 않는다(바꾸면 계약 PR).
